# ADR-189 — Medication: механизм аптечек, режимов и курсов приёма

- **Дата**: 2026-09-04
- **Статус**: принято; **фазы A–D реализованы** (миграции 095, 096; умный ввод — rule-парсер без LLM-слоя; см. K-MEDICATION-COURSES-SPEC)
- **Связано**: ADR-084 (Medication Organizer), PD-013 (relief-only), ADR-188

## Контекст

Разбор `/medications` (страница + сервис + модель) показал:

1. **Аптечки не видны**: список рендерится только внутри свёрнутого `<details>` блока
   «Добавить аптечку», без содержимого и метаданных.
2. **Препарат нельзя сразу положить в аптечку**: форма `POST /medications` не принимает
   `kit_id`; привязка возможна только через отдельный шаг «добавить партию».
3. **Режим приёма — текст**: поле `instructions` + разрозненные поля формы без привязки
   к еде, без длительности в днях, без пресетов и предпросмотра плана.
4. **Нет курсов**: невозможно спланировать приём одного препарата или комплекса с общим
   графиком и автогенерацией плана.

## Решение

1. **Аптечки**: отдельная всегда-видимая секция с карточками; в форму препарата добавляется
   select «Аптечка» + «Остаток» → автосоздание партии (`MedStock`) при сохранении.
2. **Режим приёма (Regimen)** — семантические параметры поверх `MedSchedule` (миграция 095):
   `food_relation` (до/после/во время еды, натощак, независимо), `duration_days`,
   `meal_timing` (JSON-переопределение времён еды), `meal_offset_min`, `course_id`.
   Времена приёма вычисляются из параметров (правила: `times_of_day` → сетка еды →
   равномерно по бодрствованию; `empty_stomach` → за 30 мин до завтрака).
3. **Пресеты режимов**: статический конфиг `REGIMEN_PRESETS` (шаблоны параметров,
   «3 раза в день до еды 20 дней» = `times_per_day=3 + before_meal + duration_days=20`);
   текстовое представление — `regimen_to_text`.
4. **Умный ввод**: два пути в одной форме — структурный (пресеты/поля) и свободный текст
   (rule-парсер + опциональное LLM-уточнение → Pydantic → предзаполнение формы).
   **Ничего не сохраняется без подтверждения пользователя** (human-in-the-loop;
   принцип гибридной генерации).
5. **Курсы (`MedCourse`)**: заголовок курса + элементы (`MedSchedule.course_id`).
   График **вычисляется на лету** сервисом `build_course_plan(course_id, from, to)`
   без материализации; `MedIntake` — журнал фактов; сводка «сегодня» использует тот же
   генератор. Перед сохранением — HTMX-превью таймлайна (дата × время × препарат × доза).

## Почему вычисляемый план, а не материализованные приёмы

- Нет дублирования истины: ожидаемые приёмы всегда выводятся из параметров расписаний,
  правка режима сразу меняет план (без регенерации и миграций данных).
- Долгие/повторяющиеся курсы не раздувают БД; `MedIntake` хранит только факты.
- Это продолжает существующий паттерн `doses_today` в `med_service.schedule_summary`.

## Последствия

- Миграция 095: новая таблица `med_courses` + 5 колонок в `med_schedules`.
- Модель: `MedCourse`; `MedSchedule` расширяется (`meal_timing` —
  `JSON().with_variant(JSONB, "postgresql")` для SQLite-совместимости).
- API: HTML-роуты курсов + `POST /medications/parse-regimen`; JSON API
  `/api/v2/medications/courses` (+`/plan`) для mobile parity.
- Relief-only (PD-013) сохраняется: геймификация не применяется, пропуск не штрафуется.
- Экспорт для врача расширяется на курсы.

## Альтернативы

- **Материализация приёмов** (генерация `MedIntake` на весь курс при создании): отклонено —
  дублирование истины, регенерация при правке, раздувание БД.
- **Только LLM-парсинг без структурной формы**: отклонено — дозировки слишком критичны
  для чёрного ящика; парсер/LLM лишь предзаполняют форму, решение всегда за пользователем.
- **Новая таблица regimen-шаблонов в БД**: отложено — пресеты пока статический конфиг,
  вынос в БД возможен позже без слома API.
