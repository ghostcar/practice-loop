# ADR-191 — Карточка медикамента, личные LLM в навигации, фикс админ-пула, журнал вызовов LLM

- **Дата**: 2026-09-08
- **Статус**: принято
- **Связано**: ADR-190 (медикаменты: вещества/состав/пределы), ADR-109 (поиск аналогов),
  ADR-162 (thin routes), ADR-033 (навигация), ADR-161/163 (сервисный слой)
- **Инициатива владельца**: (1) после добавления медикамента нет возможности посмотреть/
  изменить его карточку; (2) настройки личных LLM не находятся в UI; (3) добавление внешней
  LLM через админку выдает ошибку; (4) нужен механизм просмотра логов ошибок LLM.

## Контекст (факты на 2026-09-08)

1. Карточка препарата на странице `/medications` была read-only: CRUD-сервис (`update_medication`,
   `med_dict`, состав) существовал, но в шаблоне не было формы редактирования и ссылок «открыть
   карточку» — после добавления препарат нельзя было ни посмотреть детально, ни изменить.
2. Страница личных LLM-настроек `/llm-configs` существовала, но **не была нигде в навигации** —
   пользователь не мог её найти; единственный путь — прямой ввод URL.
3. Админ-пул `/admin/llm-pool` падал с `MissingGreenlet` при обращении к
   `LLMGlobalProvider.models` вне сессии; добавление провайдера с уже существующим именем
   завершалось ошибкой без человекочитаемого сообщения.
4. `LLMUserSelection` хранил `portal_provider_id` в формате `"{id} (local)"` (устаревший формат);
   resolver не распознавал его и не делал фолбэк — при выборе провайдера возникал сбой.
5. Ошибки LLM-вызовов (задачи, инсайты, диета, тренировки, медикаменты и т.д.) видны только
   в docker-логах; пользовательского журнала не было.

## Решения

1. **Карточка медикамента — просмотр и редактирование**. Каждая карточка на `/medications`
   получает якорь `#med-{id}`, кнопку «Открыть карточку» (разворачивает детальный блок) и
   форму редактирования: наименование, производитель, форма, дозировка, вид, аптечка/локация,
   заметки, состав (субстанция/доза/единица), `allow_ul_override`. POST → существующий
   `update_medication` (thin route), редирект на якорь карточки. Состав редактируется целиком
   (recreate компонентов), вещества переиспользуются через `find_or_create_substance`.
2. **Личные LLM-настройки — в главной навигации**. Пункт меню (иконка `icon`-пакета, ключ
   `nav_llm`) ведёт на `/llm-configs`; заголовки страниц обновлены.
3. **Фикс админ-пула LLM**. Загрузка `provider.models` — с eager-загрузкой (`selectinload`)
   в рамках сессии; дубликат имени → локализованное сообщение об ошибке вместо 500.
4. **Фолбэк устаревшего portal id**. Resolver распознаёт суффикс `" (local)"` и делает
   фолбэк на legacy-конфиг; данные `llm_user_selections` с устаревшим форматом чинятся
   на лету. Проверено на реальном PostgreSQL.
5. **Журнал вызовов LLM** (миграция `099_llm_call_logs`): таблица `llm_call_logs`
   (user_id, provider_name, model_name, capability, section, purpose, status, error_message,
   prompt_tokens/completion_tokens/total_tokens, cost, duration_ms, created_at, index).
   Запись — внутри `call_llm` (успех и ошибка) и во всех call-сайтах, где вызов идёт мимо
   `client.call_llm` (agent/core, agent/verify, locktimer_proposals, pipeline/*);
   `raw` не хранится (принцип ADR-034). Страница `/llm-configs/logs` (фильтр ok/error,
   статистика токенов/стоимости) + JSON-parity: `/llm-configs/logs/json` и
   `/api/v2/llm/logs`.
6. **Фикс удаления препарата**: `Medication.components/variants` получили
   `cascade="all, delete-orphan", passive_deletes=True` — ORM больше не пытается обнулить
   NOT NULL foreign keys (устранена ошибка 500 NotNullViolation). Маршрут удаления перехватывает
   ошибки и возвращает понятные уведомления.
7. **Авто-расписание из поля «Как принимать»**: функция `maybe_schedule_from_instructions`
   автоматически создаёт `MedSchedule`, если режим распознан и расписаний ещё нет.
8. **Объединение приёма по слотам**: блок «На сегодня» переведён на `summary.slots` с
   пакетным приёмом всех препаратов одного времени (`/med-intakes/batch`).

## Последствия

- **Найден и исправлен при ревью (2026-09-08)**: `app/agent/core.py` и
  `app/agent/verify.py` вызывали `call_llm(..., messages=..., tool_choice=...)` — сигнатуры,
  которой никогда не было (TypeError при каждом запуске агента; баг предшествовал ADR-191,
  но не был замечен, т.к. агент не покрыт тестами). `call_llm` расширен параметром
  `messages` (полный список сообщений OpenAI, multi-turn — для второго хода агента с
  историей tool-вызовов); первый ход агента и verify переведены на
  `system_prompt`/`user_message`. Добавлены тесты (`tests/test_agent_llm.py`): messages=
  используется как есть, отсутствие обоих способов → ValueError, сигнатура первого хода
  агента. Регрессия 1533 passed / 4 skipped.
- Карточка препарата становится источником правды для состава — UI и JSON-пути
  (`/api/v2/medications`) используют один сервисный слой.
- Навигация «6 пунктов» (ADR-033) расширяется пунктом LLM-инструментов без удаления существующих.
- Журнал LLM пишется в БД на каждый вызов — рост таблицы ограничен (логируются метаданные,
  не raw-ответы); страница отдаёт последние 200 записей, JSON — до 500.
- Ошибки LLM становятся диагностируемыми самим пользователем без доступа к серверу.
