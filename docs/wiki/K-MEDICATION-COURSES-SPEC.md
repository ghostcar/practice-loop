# K-MEDICATION-COURSES-SPEC — Механизм «Аптечки + Режимы + Курсы приёма»

> Статус: **фазы A, B, C и D реализованы** (2026-09-04).
> Модуль: Medication Organizer (§22 FUNCTIONAL.md, ADR-084). Relief-only (PD-013):
> геймификация не применяется, все записи — Private Record (DATA_LIFECYCLE.md).

## 1. Проблема (диагностика текущего состояния)

| # | Проблема | Факт в коде |
|---|---|---|
| 1 | Аптечка не видна, пока не нажать «Добавить аптечку», и выглядит невзрачной строкой | Список аптечек рендерится **только внутри свёрнутого** `<details>` блока добавления (`medication.html`): без клика невидим; строка = имя + локация + кнопка удаления, без содержимого и метаданных |
| 2 | При добавлении препарата нельзя сразу указать аптечку | Форма `POST /medications` не принимает `kit_id`; аптечка выбирается лишь на шаге «добавить партию» (`POST /medications/{id}/stock`) внутри коллапса |
| 3 | «Как принимать» — текстовое поле `instructions` + разрозненные поля формы | `MedSchedule.instructions` (Text); форма расписания: `frequency_type`, `times_per_day`, `times_of_day` (сырой текст «08:00, 20:00»), `start/end_date`. Нет привязки к еде, нет длительности в днях, нет пресетов, нет предпросмотра плана |
| 4 | Нельзя спланировать курс (один препарат или комплекс) с автографом | Нет сущности курса; `MedSchedule` не связаны между собой; план приёмов не генерируется (есть только `doses_today` — число доз на день) |

Данная модель уже содержит: `medications`, `med_kits`, `med_stocks` (партия + `kit_id`),
`med_schedules` (доза + частота daily/interval/weekly), `med_intakes` (факт приёма).
Механизм достраивается поверх неё, без слома существующего.

## 2. Целевая модель

### 2.1. Аптечки (UI-фикс + поток «препарат → аптечка»)

- **Отдельная секция «Аптечки»** на `/medications`, всегда видимая: карточка аптечки =
  имя, локация, заметки, число препаратов, список препаратов (через партии), ближайший
  срок годности. CRUD сохраняется.
- **Форма добавления препарата** получает: `select` «Аптечка» + необязательное поле
  «Остаток». Если выбрана аптечка — при создании препарата **автосоздаётся партия**
  (`MedStock` с `kit_id`, `quantity` из поля, иначе 0).

### 2.2. Режим приёма (Regimen) — семантические параметры

`MedSchedule` расширяется (миграция 095), новое:

| Поле | Тип | Смысл |
|---|---|---|
| `food_relation` | `VARCHAR(20)` | `before_meal` / `after_meal` / `during_meal` / `empty_stomach` / `independent` |
| `duration_days` | `INT` | длительность в днях (если задано и нет `end_date`: `end_date = start_date + duration_days − 1`) |
| `meal_timing` | `JSON` | переопределение дефолтных времён еды: `{"breakfast": "08:00", "lunch": "13:00", "dinner": "19:00"}` |
| `meal_offset_min` | `INT` | сдвиг приёма относительно еды (минуты; дефолт по пресету: до еды −30, после +15) |
| `course_id` | `UUID NULL` | FK → `med_courses.id` (элемент курса), `ON DELETE SET NULL` |

Существующие поля частоты остаются источником графика:
`frequency_type` (daily/interval/weekly), `times_per_day`, `times_of_day`,
`interval_hours`, `days_of_week`, `start_date`, `end_date`, `dose_quantity`, `dose_unit`.

**Правила генерации времён приёма (для daily):**
1. Если `times_of_day` задано → использовать как есть.
2. Иначе если `times_per_day` ≤ 3 и `food_relation != independent` → распределить по сетке
   еды (`breakfast/lunch/dinner` из `meal_timing` или дефолт) со сдвигом `meal_offset_min`.
3. Иначе если задано `times_per_day` → равномерно по бодрствованию (08:00–22:00).
4. `empty_stomach` → 1 приём за 30 мин до завтрака (дефолт; offset переопределяем).

### 2.3. Пресеты режимов (предопределённые варианты)

Статический конфиг в `med_service` (`REGIMEN_PRESETS`), расширяемый. Каждый пресет —
**шаблон параметров**; недостающее пользователь заполняет (доза, времена, длительность,
старт). Комбинация параметров полностью определяет режим; текстовое представление
генерируется функцией `regimen_to_text(params)`.

| Ключ | Параметры | Пример текста |
|---|---|---|
| `once_morning` | 1 р/д, независимо, утро (08:00) | «1 раз в день, утром» |
| `once_empty_stomach` | 1 р/д, натощак | «натощак, за 30 мин до завтрака» |
| `twice_before_meal` | 2 р/д, до еды | «2 раза в день до еды» |
| `three_before_meal` | 3 р/д, до еды | «3 раза в день до еды» |
| `three_after_meal` | 3 р/д, после еды | «3 раза в день после еды» |
| `interval_hours` | каждые N часов | «каждые 6 часов» |
| `weekly_days` | по дням недели | «по понедельникам/средам/пятницам» |
| `course_fixed` | N дней с даты | «20 дней, с 15.09» (duration_days + start_date) |

### 2.4. Умный ввод (интерактивно-интеллектуальный) — реализован

Два взаимодополняющих пути в одной форме:

1. **Структурный**: пресет-чипы + поля (раз в день, привязка к еде, времена, длительность,
   старт, доза) → живое текстовое превью `regimen_to_text`.
2. **Свободный текст**: поле «Как принимать?» («3 раза в день до еды 20 дней»,
   «1 таблетка каждые 6 часов с понедельника») → детерминированный rule-парсер
   (число раз, до/после/во время еды, натощак, каждые N ч, N дней, дата старта)
   → опциональное LLM-уточнение (BYOK, режим `abstract`-безопасный) → **Pydantic-валидация**
   → результат заполняет структурную форму, которую пользователь **подтверждает перед
   сохранением** (human-in-the-loop, принцип гибридной генерации проекта).

Парсер не сохраняет ничего сам: вывод — только предложенные параметры в форме.

### 2.5. Курсы приёма (MedCourse)

Новая таблица `med_courses`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | UUID PK | |
| `user_id` | UUID FK users | owner |
| `name` | VARCHAR(200) | название курса («Курс витаминов», «Антибиотик + пробиотик») |
| `notes` | TEXT | заметки |
| `start_date` | DATE | старт курса |
| `end_date` | DATE NULL | вычисляется = max(end_date) по элементам |
| `status` | VARCHAR(20) | `planned` / `active` / `completed` / `paused` |
| `is_active` | BOOL | |
| `created_at` / `updated_at` | | |

Курс = 1..N элементов `MedSchedule` (каждый: препарат + свой режим, `course_id`).
Один и тот же препарат может быть в нескольких курсах/расписаниях.

**Автосоставление графика — `build_course_plan(course_id, from_date, to_date)`**:
вычисляемый план без материализации (по аналогии с существующим `doses_today`):
для каждой даты диапазона → список `(medication, time, dose, food_relation)`.
`MedIntake` остаётся журналом **фактов**; «ожидание» всегда выводится из параметров
расписаний. Сводка «на сегодня» использует тот же генератор → элементы курса
автоматически попадают в due-today и reminders.

**Предпросмотр**: перед сохранением курса HTMX-рендер таймлайна
(дата × время × препарат × доза) — система показывает, что она «поняла» запрос.

**Факт (фаза D, реализована 2026-09-04)**: поле «Напишите как принимать» над
пресетами в обеих формах (расписание препарата и «добавить препарат в курс») +
кнопка «Разобрать» → `POST /medications/parse-regimen` (страница) / `POST
/api/v2/medications/regimen/parse` (mobile parity) → `parse_regimen_text`
(детерминированный rule-парсер RU/EN: N раз в день, до/после/во время еды,
натощак, каждые N часов, N дней, по дням недели/будням, с даты/дня недели,
явные времена, утро/вечер, доза в начале) → параметры заполняют форму → живой
превью-текст → **подтверждение перед сохранением**. Парсер ничего не сохраняет;
LLM-уточнение остаётся опциональным слоем поверх (не подключён — детерминированный
разбор покрывает целевые формулировки).

## 3. Миграции (факт)

**095_med_regimen_fields (реализована, фаза B)** — только поля режима:

```
ALTER TABLE med_schedules
    ADD COLUMN food_relation VARCHAR(20),
    ADD COLUMN duration_days INTEGER,
    ADD COLUMN meal_timing JSON,
    ADD COLUMN meal_offset_min INTEGER;
```

**096_courses_kit_locations (реализована, фаза C)** — курсы: `CREATE TABLE
med_courses` (id, user_id, name, notes, start/end_date, status planned|active|
completed|paused, is_active) + `course_id` на `med_schedules` (FK, ON DELETE
SET NULL) + `location_id` на `med_kits` (FK → `task_locations`, ON DELETE
SET NULL) + индексы; downgrade зеркально. Roundtrip проверен на живом PostgreSQL.

Модели: `MedSchedule` расширен (`meal_timing` — `JSON().with_variant(JSONB, "postgresql")`
для SQLite-совместимости); добавлены `MedCourse`, `MedKit.location_id` +
relationship `linked_location` (legacy text-колонка `med_kits.location` сохранена
как fallback-подпись); `location_path()` + `kit_location_label()` — путь
«Квартира / Комната / Место».

## 5. UI-потоки (эскиз)

1. **Секция «Аптечки»** — карточки сверху страницы (или своя секция): имя, локация,
   список препаратов, счётчики. «+ Аптечка» раскрывает форму (как сейчас).
2. **Форма препарата** — select «Аптечка» + «Остаток» (необязательно).
3. **Форма режима** — чипы пресетов → структурированные поля → живой текст
   «3 раза в день до еды · 20 дней · с 15.09» → «Предпросмотр плана».
4. **Секция «Курсы»** — карточки курсов (имя, период, прогресс принято/всего),
   «+ Новый курс»: имя → добавить препараты по одному (каждый со своим режимом) →
   старт → превью таймлайна → сохранить.

## 7. Безопасность и границы

- Дозировки и режимы — **медицинские данные, ввод пользователя подтверждается** перед
  сохранением (никаких авто-сохранений из парсера/LLM).
- LLM-уточнение работает только как «предзаполнение формы» (human-in-the-loop);
  обход safety-фильтров не реализуется, контент режимов — обычный структурированный ввод.
- Relief-only (PD-013): пропуск приёма не штрафуется (существующее правило сохранено).
- Экспорт для врача (CSV/JSON) расширяется на курсы (Фаза D, `get_json_export`).
