# Спецификация: Consensual Adult Activity & LLM Tracker

> Файл-спецификация по итогам интервью (5 раундов). Источник исходных требований — `AGENTS.md`.
> Название проекта (рабочее): **tracker**.

---

## 1. Резюме

Веб-приложение для личного отслеживания и управления активностями в парных/личных отношениях
(только для взрослых, по обоюдному согласию). Приложение хранит каталог задач (активностей),
ведёт сессии и историю, применяет геймификацию (XP, уровни, достижения) и штрафы (игровые +
настраиваемые реальные последствия). LLM-модель подбирает задачу и её параметры из **каталога,
одобренного пользователем**, опираясь на предыдущие результаты.

Текущая цель — **личное использование** (один пользователь), но архитектура и модель данных
сразу проектируются с расчётом на **мультипользовательское взаимодействие** (совместные задачи,
общий каталог, обезличенная доска достижений).

---

## 2. Ключевые принципы (из интервью)

1. **Гибридная генерация, без обхода safety-фильтров.**
   Концепция «Semantic Masking» из AGENTS.md (кодирование контента с целью обмана safety-фильтров
   провайдера) **отклонена** — такие механизмы нарушают ToS провайдеров (риск блокировки ключа).
   Вместо этого:
   - Все задачи формируются пользователем/админом в каталоге и **осознанно одобрены** пользователем
     как приемлемые и допустимые.
   - LLM **не генерирует откровенный контент**, а выбирает «условно произвольную» задачу из
     допустимого набора и подбирает параметры на основе истории.
   - Система работает только с личным пространством пользователя, не нарушает законов.
2. **Мультиязычность.** UI на русском и английском, с возможностью добавления новых языков (i18n).
3. **BYOK (bring your own key).** Поддержка любых **OpenAI-совместимых** провайдеров через
   настраиваемый `api_base_url` (OpenAI, Groq, OpenRouter, VLLM, Ollama и т.п.). Схема
   `LLMProviderConfig` уже это предусматривает.
4. **Сейчас — один пользователь, завтра — SaaS.** `subscription_tier` остаётся полем-заглушкой
   (без оплаты и тарифной логики), но модель пользователей и сессий сразу поддерживает
   межпользовательское взаимодействие.
5. **Комплаенс и приватность.** Подтверждение возраста, честная маркировка контента, экспорт/удаление
   данных. Обезличенная доска достижений.

## 3. Целевая аудитория и сценарии

- **Сейчас:** один пользователь (автор). Простая регистрация (email+пароль), без подтверждения email.
- **Потом:** ограниченный круг (партнёры, друзья) → возможно, публичный доступ.

Сценарии:
1. Пользователь просматривает каталог задач, отмечает допустимые для себя (опт-ин).
2. Пользователь запускает **сессию** (одну или с партнёром), задаёт правила/штрафы.
3. LLM предлагает задачу + параметры из допустимого набора с учётом истории и статистики.
4. Пользователь выполняет задачу или **прерывает** её (со штрафом, настроенным заранее).
5. Ведётся статистика: XP, уровни, серии (streaks), достижения, история.
6. Уведомления: in-app + Telegram-бот.
7. Пользователь может экспортировать/удалить данные; может оставить обезличенные данные
   для публичной доски достижений.

## 4. Технологический стек

- **Backend:** Python 3.11+, FastAPI (async), Uvicorn, Pydantic v2.
- **DB:** PostgreSQL 15. ORM: SQLAlchemy 2.0 (async) + Alembic.
- **Frontend:** SSR Jinja2 + HTMX + TailwindCSS (без тяжёлых JS-фреймворков).
- **LLM:** `openai` SDK (OpenAI-совместимые endpoints). JSON repair — `json_repair` + regex-фолбэк.
- **Стартовые провайдеры:** **Omniroute** (локальный шлюз на хосте VPS, OpenAI-совместимый
  `http://host.docker.internal:20128/v1`, модель по умолчанию `auto` — умная маршрутизация по ~2000 моделям,
  бесплатные и платные), Groq (быстрый бесплатный тир, Llama, нативный JSON mode), OpenRouter (агрегатор с фолбэком).
  Активный по умолчанию — **Omniroute**.
- **Telegram:** бот для уведомлений на **aiogram 3.x** (вебхук в FastAPI + исходящие уведомления из фоновых задач).
- **Деплой:** Docker + Docker Compose (app, PostgreSQL, Nginx с SSL), `.env` для секретов.
- **Бэкапы:** pg_dump по cron в контейнере, хранение последних N копий.
- **Тесты:** pytest — тщательные: unit + интеграционные (эндпоинты, БД, LLM-пайплайн с моками).

## 5. Архитектура (уточнённая)

### 5.1. Гибридный пайплайн генерации (замена Semantic Masking)

```
Каталог Entity (задачи + schema параметров)
        │  пользователь отмечает допустимые (опт-ин)
        ▼
Context Builder (статистика, история, активные штрафы, допустимый набор)
        ▼
LLM (провайдер из LLMProviderConfig): выбор задачи + параметры
        ▼
JSON → json_repair → Pydantic-валидация → сохранение в ActivityLog
        ▼
UI: пользователь видит реальную задачу (без кодирования)
```

- LLM **видит реальные названия задач**, поскольку пользователь сам их одобрил — это
  осознанное согласие, а не обход фильтров. Никаких `system_code` / нейтральных масок.
- Промпт-инструкция: «выбери одну задачу из предоставленного списка, укажи параметры в заданных
  диапазонах, обоснуй выбор на основе истории».
- **Stateless:** каждый запрос собирает контекст заново (история, штрафы, допустимый набор).
- **Tool calling** остаётся опцией: `save_activity_log`, `get_user_stats`, `apply_penalty`.

### 5.2. Обработка ошибок LLM

1. Попытка `json.loads`.
2. Неудача → `json_repair`.
3. Неудача → regex-извлечение из markdown-блока.
4. **3 неудачные попытки подряд → пользователю показывается ошибка и кнопка «Повторить».**
   (Выбран вариант «Ошибка + повтор», а не шаблонная подстановка.)

### 5.3. Биллинг использования моделей

- `raw_llm_response` хранится **полностью** — в т.ч. для **биллинга моделей** (BYOK: пользователь
  платит за свой ключ). Нужен подсчёт токенов и стоимости по каждому `LLMProviderConfig`.

## 6. Схема БД (уточнённая)

Базовые сущности из AGENTS.md + уточнения по интервью:

### Users & Billing
- `User`: id, email, password_hash, `subscription_tier` (**поле-заглушка**, без логики оплаты),
  locale, theme (dark/light), created_at.
- `LLMProviderConfig`: id, user_id, provider_name, api_base_url, api_key (шифруется), model_name,
  is_active, usage-статистика (суммарные токены/стоимость).

### Каталог задач (Entity)
- `Entity`: id, type, real_name, category, tags (JSON), owner_id (NULL = системный), is_public,
  **author_id/авторство** (для публичных), params_schema (JSON: длительность, интенсивность,
  повторяемость, участники, кастомные параметры, **фазы/итерации с таймером**), created_at.
  Типы: разовая / серийная / бесконечная (рутина).
- Каталог наполняют: **админ** (seed 30+ задач) и **пользователи** (личные задачи, возможность
  опубликовать с указанием авторства).
- Опт-ин: да/нет + рейтинг (1–5) + категории + **шкала желания** (от «очень хочу» до
  «недопустимо»; «недопустимо» — ненулевая вероятность попадания в предложения LLM;
  «нет» — полное исключение).

### Сессии и логи
- `ActivitySession`: id, owner_id, **участники (many-to-many)**, status (`created`/`active`/`ended`),
  llm_config_id, правила сессии (JSON: штраф за прерывание, лимиты задач/таймер, получатели
  уведомлений, эскалация штрафов, параллельные задачи), started_at, ended_at.
- `ActivityLog`: id, session_id, user_id, entity_id, status (выполнено / **прервано**),
  user_prompt, `raw_llm_response` (**полностью**), cleaned_response, penalty_applied,
  penalty_details (JSON), usage (tokens/cost), created_at.

### Геймификация
- `Achievement` (код, название, условия, **SVG-иконка**), `UserAchievement` (user_id, achievement_id,
  obtained_at, контекст получения, скрыто ли на доске).
- **Доска достижений**: комбинированная — лента всех (обезличенная) + топ-лист + «мои достижения»;
  публичный ник (по умолчанию «Аноним»), отдельные достижения можно скрывать.
- История получения: по умолчанию дата; контекст (задача/сессия) — по желанию пользователя.
- Уровни: фиксированные пороги XP — 0/100/250/500/1000/1750/2750/4000/5500/7500/10000/13000/16500/20500/25000, далее +2500 за уровень (точная таблица — раздел 9.5).
- XP/серии/комбо — формулы по умолчанию заданы в `app/gamification/xp.py` (раздел 9.5); настраиваемые в правилах/профиле.

### Штрафы (детализация)
- Штраф за прерывание настраивается **в самой задаче**: фикс XP / % от XP / множитель.
- При прерывании возможна **автоматическая генерация** новой задачи с усложнением или упрощением.
- Эскалация штрафов: множитель растёт с пропусками (×1, ×1.5, ×2…); настраивается сброс
  (да/нет) и уровень сброса при выполнении (например −2).
- Совместные сессии: применение штрафов/бонусов настраивается (нарушителю / всем участникам).
- Подробности — раздел 9.

## 7. Функциональные требования (по фазам)

- Подсчёт токенов/стоимости по конфигу (для биллинга моделей).
- Генерация контента **на языке пользователя** (locale из профиля передаётся в промпт).

### Phase 4 — UI, сессии, геймификация, уведомления
- HTMX-эндпоинты: дашборд, история, статистика, доска достижений (обезличенная).
- Механика **сессий**: создание, участники, правила, статусы; совместные задачи.
- Выполнение/прерывание задачи со штрафом.
- Геймификация: XP, уровни, серии, достижения, бейджи.
- Кастомные правила (настраиваются): формулы XP; правила сессий («пропустил 2 задачи подряд → штраф X»,
  «прервал → +усложнение»); множитель серий (streak); эскалация штрафов; недельные челленджи с наградами;
  комбо-бонус за цепочку задач без прерываний; редкие случайные бонус-задачи с удвоенным XP;
  совместные достижения для общих сессий.
- Уведомления: in-app + Telegram-бот (напоминания, штрафы, события сессии).
- Приватность: экспорт данных, удаление аккаунта (полное), удаление аккаунта с сохранением
  обезличенных данных.

## 8. Telegram-бот (детализация)

### 8.1. Режим и интеграция
- **aiogram 3.x**, вебхук: `POST /tg/webhook` через nginx, secret token из `.env` (без поллинга).
- Бот **интерактивный**: команды и inline-кнопки в Telegram.
- Язык сообщений — по locale пользователя.

### 8.2. Команды
- `/next` — сгенерировать новую задачу через LLM. **Параллельная задача**: если правила сессии
  позволяют — создаётся вторая задача параллельно; если нет — отказ с пояснением.
- `✅ /done` — отметить задачу выполненной; после нажатия — **необязательный комментарий**.
- `⏹ /interrupt` — прервать задачу (со штрафом).
- `📊 /stats` — статистика: XP, серии, челленджи.
- `🎯 /session` — показать/создать сессию, статус.
- `⚙️ /settings` — настройки: интервал напоминаний, язык.

### 8.3. Уведомления (все 5 типов)
1. Напоминания о задаче — **интервальные** (каждые N часов, пока задача активна; старт 2 ч,
   настраивается в профиле).
2. События сессий (старт/конец, новая задача, события партнёра).
3. Штрафы и прерывания.
4. Челленджи и серии (прогресс, комбо).
5. Достижения и бонусы (новый уровень, бейдж, случайная бонус-задача).

### 8.4. Привязка аккаунта
- В профиле веба показывается **код привязки**; пользователь отправляет его боту → бот связывает
  `chat_id` с аккаунтом. Непривязанным пользователям — сообщение «привяжите аккаунт».

### 8.5. Работа с задачами
- Несколько активных задач: бот показывает **список кнопками**, пользователь выбирает.
- Карточка задачи — **компактная**: название, параметры, кнопки ✅/⏹.

### 8.6. Совместные сессии
- Получатели уведомлений настраиваются в правилах сессии (по умолчанию — все участники).

## 9. Сессии и штрафы (детализация)

### 9.1. Жизненный цикл
- Статусы: `created` → `active` → `ended`. Пауза не предусмотрена.

### 9.2. Правила сессии (настраиваемые)
- Штраф за прерывание (механика и размер).
- Лимиты: максимум задач в сессии и/или таймер.
- Получатели уведомлений: владелец / все участники / выборочно.
- Эскалация штрафов: вкл/выкл, шаг, потолок, правила сброса.
- Параллельные задачи: разрешён ли `/next` при активной задаче.

### 9.3. Штраф за прерывание
- Настраивается **в самой задаче**: фикс XP / % от XP задачи / множитель.
- Может запускать **автоматическую генерацию** новой задачи с усложнением или упрощением.

### 9.4. Совместные сессии
- Применение штрафов/бонусов: только нарушителю / всем участникам / по правилам сессии.

### 9.5. Формула XP (текущая реализация — `app/gamification/xp.py`)

XP за выполнение одной задачи считается так:

```
base = BASE_XP[тип_задачи]                 # one_time: 25 · series: 50 · infinite: 15
streak_bonus = streak_days × 5             # +5 XP за каждый день активной серии
combo_bonus = base × min(combo_count × 0.10, 0.50)   # +10% за задачу без прерываний, потолок +50%
intensity_bonus = base × (intensity − 1) × 0.10      # +10% за каждый уровень интенсивности выше 1

XP = base + streak_bonus + combo_bonus + intensity_bonus
```

- `intensity` берётся из `selected_params.intensity` (по умолчанию 1).
- **Серии (streak)**: увеличиваются не чаще раза в календарный день; сбрасываются, если
  предыдущая активность была позже, чем вчера (`should_reset_streak`); сохраняется
  `longest_streak`. Ачивки серий на 3/7/14/30/100 дней.
- **Комбо**: растёт на +1 за каждое выполнение, **сбрасывается при прерывании**; множитель
  капается на +50%.
- **Training-режим** (задача привязана к `training_day_id`): серии и комбо НЕ трогаются,
  но XP начисляется.
- **Points v2**: если у сущности есть `gamification_config`, дополнительно начисляются
  баллы по гибкой схеме (см. 9.9) — XP и баллы независимы.
- При прерывании: база штрафа `base_penalty = 25 XP`, `penalty_xp = base_penalty × эскалация`
  (см. 9.3/9.6), вычитается из XP (не ниже 0), комбо сбрасывается. Если у сущности есть
  `gamification_config` — дополнительно списываются баллы (points) по схеме 9.9.

#### Уровни

Фиксированные кумулятивные пороги (XP, необходимый для достижения уровня):

| Уровень | XP | Уровень | XP |
| --- | --- | --- | --- |
| 1 | 0 | 9 | 5 500 |
| 2 | 100 | 10 | 7 500 |
| 3 | 250 | 11 | 10 000 |
| 4 | 500 | 12 | 13 000 |
| 5 | 1 000 | 13 | 16 500 |
| 6 | 1 750 | 14 | 20 500 |
| 7 | 2 750 | 15 | 25 000 |
| 8 | 4 000 | 16+ | +2 500 за уровень |

- Пороги заданы в `LEVEL_THRESHOLDS` (15 уровней); после 15-го каждый следующий уровень
  стоит дополнительно 2 500 XP.
- Уровень пересчитывается после каждого начисления/списания XP.

### 9.6. Эскалация штрафов
- Множитель растёт с каждым пропущенным/прерванным штрафом: `mult = 1.0 + (escalation − 1) × 0.5`
  (×1, ×1.5, ×2, …), потолок ×5.
- Настраивается: сбрасывается ли при успешном выполнении и на сколько уровней (например −2).

### 9.7. Комбо
- +10% XP за каждую задачу без прерываний, потолок +50%; прерывание сбрасывает комбо.

### 9.8. Недельные челленджи
- Авто-предложения («7 задач за неделю») + ручное создание (цель, срок, награда).

### 9.9. Points v2 — гибкая схема баллов (текущая реализация — `app/gamification/points_v2.py`)

Параллельно с XP действует независимая система баллов. Если у сущности заполнен
`gamification_config` (JSON на `Entity`), при выполнении/прерывании задачи начисляются
**баллы (points)** по гибкой схеме — в дополнение к XP. Схема типизирована
Pydantic-моделями (`app/schemas/points_v2.py`) и валидируется при сохранении.

Структура `gamification_config`:

```jsonc
{
  "points": {                     // начисление за выполнение
    "base": 10,                   // базовые баллы
    "max_per_day": 50,            // зарезервировано (в схеме, в движке не применяется)
    "profile_id": null,           // UUID PointsProfile (если назначен)
    "formula": null               // зарезервировано под кастомную формулу
  },
  "penalties": {                  // штраф за прерывание (см. 9.3/9.6)
    "enabled": true,
    "levels": [                   // условия по типу срыва
      {
        "level": 1,
        "deduction": 5,           // баллов
        "condition": "missed",    // missed / partial / late (whitelist)
        "redemption": {           // опциональная «отработка» штрафа
          "type": "clothespins",
          "duration_min": 10,
          "count": 0,
          "description": ""
        },
        "auto_apply": true
      }
    ],
    "escalation": false,
    "escalation_step": 1.5,
    "escalation_cap": 5
  },
  "bonuses": [                    // бонусные условия (typed DSL, без eval)
    {
      "code": "extra_fluid",
      "condition": "extra_fluid_ml > 0",  // "поле оператор значение" | простое поле
      "reward": 20,
      "per_unit": false,          // true → reward × количество по полю условия
      "description": "",
      "enabled": true
    }
  ],
  "thresholds": {                 // пороги баланса → авто-уведомления
    "negative": -100,
    "warning": 0,
    "good": 100
  }
}
```

#### Начисление (выполнение задачи)

```
base = points.base × (1 + (intensity − 1) × 0.10)   // интенсивность из params
bonus = Σ reward (для каждого сработавшего bonus.condition)
        × (per_unit ? количество по полю условия : 1)
points = base + bonus_total
```

- Условия бонусов — **типизированный DSL без `eval`** (`app/gamification/dsl.py`):
  whitelist операторов `> < >= <= == !=`, поле `[A-Za-z_][A-Za-z0-9_]*`, значение —
  число / `true|false` / короткая строка в кавычках.
- Транзакция пишется в `PointsTransaction` (`transaction_type=earn`) с уникальной
  привязкой к `activity_log_id` (двойное начисление невозможно).

#### Штраф (прерывание)

- `penalty = deduction` уровня с `condition == "missed"` × эскалация (см. 9.6).
- Баланс не опускается ниже −1000; пишется транзакция `penalty`.
- Если у уровня задан `redemption` — создаётся запись `PenaltyRedemption`
  (`pending`), которую можно **отработать**: `/api/v2/points/redemptions/{id}/complete`
  возвращает `points_value` баллов (транзакция `redeem`); `skip` — без возврата.

#### Траты и профили

- `/api/v2/points/spend` — списание баллов на награду (`spend`).
- **PointsProfile** — переиспользуемые шаблоны `gamification_config`;
  `POST /api/v2/points/entities/{id}/assign-profile` копирует конфиг профиля в сущность
  и проставляет `points.profile_id`.

#### Пороги (thresholds)

- После каждого начисления баланс сверяется с порогами сущности (только свои/публичные
  сущности — защита от cross-user утечки):
  - `balance < negative` → уведомление «Critical points» (ограничения активны);
  - `balance < warning` → «Low points»;
  - `balance >= good` → «Points milestone».
- Пороги приходят в `GET /api/v2/points/balance` → UI подсвечивает статус.

## 10. Каталог задач (детализация)

### 10.1. Структура задачи
- Категория (фиксированный список, расширяется админом) + свободные теги.
- Тип: разовая / серийная (N повторов, прогресс по каждому) / бесконечная (рутина).

### 10.2. Параметры (params_schema)
- Длительность (диапазон минут), интенсивность (1–5 с описанием уровней), повторяемость,
  участники (1–2), кастомные параметры (JSON).
- **Итерационные шаблоны с фазами**: задачи-циклы с таймером («удержание 20с → пауза 5с →
  удержание 30с»), несколько итераций; прогрессивные серии; шкалы интенсивности.

### 10.3. Опт-ин и уровень желания
- да/нет + рейтинг (1–5) + категории + шкала желания: от «очень хочу» до «недопустимо».
- «Недопустимо» — ненулевая вероятность попадания в предложения LLM; «нет» — полное исключение.
- LLM учитывает уровень желания при выборе задачи.

### 10.4. Публикация
- Мгновенная, без модерации, с указанием авторства.

### 10.5. Стартовый набор 30+ (черновик — пользователь расширит)

| Категория | Примеры задач |
| --- | --- |
| Внимание и забота | тёплое сообщение-комплимент; массаж плеч 10–20 мин; напиток/угощение партнёру; выслушать о дне без телефона; мелкий сюрприз в течение дня |
| Романтика | вечер при свечах; фильм/сериал с обсуждением; письмо/записка с тёплыми словами; ужин вдвоём без гаджетов; прогулка за руку 30–60 мин |
| Игры и развлечения | настольная игра; игра «вопрос-ответ»; совместное хобби 30 мин; викторина друг о друге; парный матч (шахматы/карты) |
| Близость и нежность | объятия 5–10 мин; поцелуйный таймер 60 сек; комплимент + прикосновение; совместный душ; 15 минут внимания только друг для друга |
| Планирование и быт | план на выходные; совместная уборка 30 мин; список целей на месяц; обсуждение планов; запланировать вылазку |
| Эксперименты (итерационные) | таймер-фазы «удержание 20с → пауза 5с → удержание 30с»; прогрессивная серия из 3 подходов; шкала интенсивности 1→3 за 10 мин; циклы со сменой ролей; серия повторов с фиксацией результата |

> Стартовый набор — нейтральные/лёгкие задачи; конкретику и расширение добавляет пользователь
> (свои задачи, кастомные параметры).

## 13. Деплой и эксплуатация (VPS)

- Docker Compose: db + app + nginx (SSL, Let's Encrypt — домен/сертификаты настраиваются).
- `.env` для всех секретов (пароли БД, JWT-ключ, Telegram-токен, дефолтные ключи).
- Бэкапы: **pg_dump по cron** внутри контейнера, хранение последних N копий, восстановление —
  проверяется.
- Команда `docker compose up` поднимает всё; health-check для проверки.
- **Omniroute** крутится на хосте вне compose (уже настроен): контейнер app обращается к нему через
  `http://host.docker.internal:20128/v1` (URL переопределяется через конфиг/`.env`).
