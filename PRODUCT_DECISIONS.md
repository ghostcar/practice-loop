# Practice Loop — продуктовые решения и границы

> Статус: нормативный продуктовый документ.
> Актуально на: 12 августа 2026 года.
> Назначение: отделять принятые решения владельца от предложений, старых спецификаций и будущих гипотез.

## 1. Как читать этот документ

Этот файл отвечает на вопрос: **что уже решено о продукте**. Он не описывает фактическую
готовность кода — для этого существует `CURRENT_STATE.md` — и не задаёт порядок поставки — для
этого существует `ROADMAP.md`.

При конфликте продуктовой формулировки этого файла с `tracker-spec.md`,
`REMEDIATION_SPEC.md`, `FUNCTIONAL.md` или пакетом `LockTimer-Agent-Pack` действует решение из
этого файла и соответствующая запись в `memory/DECISIONS.md`.

Статусы: **принято** — входит в целевую модель; **отложено** — возможно, но не текущее
обязательство; **требует решения** — развилка не закрыта; **не входит** — сознательная граница.

## 2. Принятые решения

### PD-001. Центр продукта — Personal

**Статус: принято.** Practice Loop — прежде всего приватный личный трекер взрослых активностей.
Первый контур обязан быть полноценным продуктом сам по себе.

### PD-002. Три контура определяются способом управления

**Статус: принято.** Personal — владение и действие; Social — ограниченные проекции без передачи
управления; D/s — конкретные полномочия над выбранной частью Personal. Community — поздняя оболочка.

### PD-003. Личный контур имеет безусловный приоритет разработки

**Статус: принято.** Сначала доводятся Tracker, Today, личные сессии, Chastity Timer, личные
журналы, уведомления, медиа, экспорт и восстановление.

### PD-004. Chastity Timer — специализированный модуль Personal

**Статус: принято.** Timer прямо предназначен для сессий ношения chastity-устройств. В интерфейсе
используются честные термины. Функциональным ориентиром служит Chaster, но Practice Loop не его
клон.

### PD-005. Игровые последствия являются содержательной функцией

**Статус: принято.** Заранее выбранные штрафы, продления, отработки и изменения баллов — функция,
а не дефект. Их допустимость определяется заранее принятым правилом и лимитами.

### PD-006. Safety/emergency stop всегда имеет технический приоритет

**Статус: принято; уточняет ADR-029 и ADR-038.** Фактическое прекращение и аварийное снятие
доступны немедленно и не блокируются штрафом, голосованием, отчётом, отсутствием сети или
решением другого пользователя.

### PD-007. Personal Telegram-бот — личный клиент продукта

**Статус: принято.** Показывает Today, задачи, Chastity Timer, напоминания и статистику, принимает
личные отметки и отчёты. Боты внешних участников — отдельный контекст (Social/D/s).

### PD-008. Social не означает передачу управления

**Статус: принято.** Social получает только подготовленную проекцию. Публикация не открывает
будущие изменения Personal.

### PD-009. D/s строится на грантах, а не на названии роли

**Статус: принято.** Для каждого гранта: объекты и поля; действия; срок; числовые и временные
пределы; необходимость подтверждения; аудит, пауза, отзыв. Роль сама по себе прав не даёт.

### PD-010. Первая внешняя Dynamics асимметрична и ручная

**Статус: принято.** Внешний submissive не является User, не получает гостевой портал. Портал
формирует текст, ведущий отправляет его вручную и вручную переносит ответ. Ручная отметка не
выдаётся за подтверждённую доставку.

### PD-011. Внешние каналы — транспорт, а не отдельный продукт

**Статус: принято.** Telegram-бот внешнего участника, e-mail и будущие каналы автоматизируют
отправку поверх работающей модели Dynamics.

### PD-012. Данные разделяются на приватные записи и проекции

**Статус: принято.** 1. Private Record; 2. Shared Dynamic Record; 3. Shared Artifact; 4. Published
Projection. Отзыв разрешения прекращает будущий доступ; продукт не обещает удалить скачанные копии.

### PD-013. Health отделён от игры

**Статус: принято; смягчено ADR-085 (17.08.2026).** Медицинские записи **никогда не отнимают
баллы и не наказываются** (негативная геймификация здоровья запрещена). **Своевременный приём
(adherence) может давать XP и достижения** — позитивное подкрепление с суточной каппой. Медицинский
сигнал может только открыть окно, смягчить, поставить на паузу или завершить активность.

### PD-014. LLM — помощник, не автономный управляющий

**Статус: принято.** LLM не расширяет права, не создаёт скрытые правила после старта, не применяет
последствия напрямую, не принимает медицинские решения. Детерминированный путь обязателен для
критических действий.

### PD-015. Один продукт, одна кодовая линия

**Статус: принято.** Никакого форка, отдельного auth или несовместимого приложения для Timer.
Профиль `timer-only` требует отдельного решения.

### PD-016. Физические устройства не управляются порталом

**Статус: принято.** Приложение показывает допустимость, хранит код/подтверждение и фиксирует
действия, но не управляет физическим замком.

### PD-017. Терминология: «lock» = «chastity», таблицы не меняем, фронт честный

**Статус: принято (12.08.2026).** «Lock» происходит от закрытия/замка — это и есть chastity.
Таблицы, код и API остаются `lock_*`; переименование таблиц и миграции **не производятся**.
Честная терминология (device, wearer, lock-on, unlock window, keyholder) даётся во **фронте,
уведомлениях и внешних текстах**; внутренние имена остаются нейтральными. Прямой Chastity Timer,
нейтральность только для discretion-уведомлений.

### PD-018. Мобильное приложение — кроссплатформенное, после базового портала

**Статус: принято (12.08.2026).** После запуска базового портала разрабатывается мобильное
приложение (кроссплатформенное: Flutter или React Native). Это полноценный клиент Personal, а не
обёртка над web. Требования закладываются с этого момента: JSON API-first, bearer-auth,
push-уведомления (помимо Telegram). Мобильный клиент — первый внешний потребитель внутреннего API.

### PD-019. Масштабирование — обязательство на всех трёх осях

**Статус: принято (12.08.2026).** Масштабирование понимается как: (1) много пользователей
(публичный доступ + Social), (2) объём данных одного пользователя (годы журналов, медиа),
(3) горизонтальная инфраструктура (несколько app-инстансов, очередь, объектное хранилище, реплика
БД). Сейчас закладываются дешёвые решения: owner-scoped как контракт, storage-абстракция,
JSON-first; остальное (rate limits, очередь, partition) — по мере реальной потребности, без
преждевременной постройки.

### PD-020. JSON-first контракт для всех новых эндпоинтов

**Статус: принято (12.08.2026).** Все новые и изменяемые action-эндпоинты возвращают JSON
(JSONResponse), а не HTML/redirect. HTMX-фронт продолжает работать, потребляя те же JSON-контракты
через fetch. HTML-рендер остаётся для страниц. Это фундамент для мобильного клиента (PD-018) и
масштабирования (PD-019).

## 3. Отложенные гипотезы

- зарегистрированные отношения и цифровая передача грантов между аккаунтами;
- открытый Community, группы и пространства;
- каталог или рынок пользовательских шаблонов;
- creator/mentor-профили и branded spaces;
- эксплуатационный профиль `timer-only`;
- self-hosted координационный узел для многопользовательского режима;
- публичный API и webhooks для третьих сторон;
- дополнительные транспортные каналы после личного Telegram и ручной Dynamics;
- OCR/LLM-верификация одноразовых кодов по фото (текущая верификация — ручной ввод кода);
- видео в Media Vault (сейчас только изображения).

## 4. Сознательно не входит

- гостевой портал для внешнего submissive в обозримом roadmap;
- произвольные исполняемые пользовательские плагины;
- скрытые или бесконечные полномочия одного пользователя над другим;
- передача гранта третьему лицу без нового согласия;
- автономный AI-keyholder, создающий новые правила после старта;
- управление физическим устройством;
- финансовые ставки, депозиты, tribute, платный выход и материальные наказания;
- медицинская диагностика, назначение лечения и изменение дозировок;
- использование медицинских данных для наказаний или публичных рейтингов;
- автоматическая публикация чувствительных данных или оригиналов приватного медиа;
- универсальный task manager для несвязанных бытовых и рабочих задач.
