# PracticeLoop v0.7 — спецификация стабилизации и исправлений

> Статус: обязательный рабочий контракт для ветки стабилизации v0.7.  
> Дата: 2026-08-07.  
> Область: backend, модель данных, планировщик, LLM-контур, безопасность и пересборка frontend.  
> Визуальные требования: `DESIGN.md`.

## 1. Назначение документа

Текущая версия PracticeLoop является функциональным прототипом. Перед тестовой эксплуатацией
необходимо остановить добавление функций, восстановить воспроизводимость проекта, зафиксировать
доменные инварианты и пересобрать основной пользовательский сценарий.

Этот документ описывает **целевое поведение**, а не текущее устройство кода. Если существующая
реализация ему противоречит, изменяется реализация.

### 1.1. Приоритет источников требований

При разработке v0.7 действует следующий порядок:

1. `REMEDIATION_SPEC.md` — продуктовые инварианты, архитектура и порядок исправлений.
2. `DESIGN.md` — интерфейс, визуальные токены, компоненты и адаптивность.
3. `AGENTS.md` — общие инженерные правила и ограничения проекта.
4. `tracker-spec.md` — историческая спецификация; применяется только в непротиворечащей части.
5. `memory/*` — статус, история и журнал решений; не является источником новых требований.

### 1.2. Цель релиза v0.7

Релиз считается успешным, если пользователь может:

1. добавить или подключить практики;
2. явно включить или выключить каждую практику;
3. задать отношение, частоту, максимальный перерыв и предел сложности;
4. получить валидный план дня/сессии только из разрешённого набора;
5. выполнить, пропустить или немедленно остановить любой пункт;
6. оставить короткую обратную связь;
7. увидеть историю и понять, почему практика попала в план.

Все вторичные возможности подчиняются этому циклу и не конкурируют с ним на главном экране.

## 2. Зафиксированные требования владельца

Следующие положения не должны переосмысливаться агентом во время реализации:

- каталог наполняется администратором и проходит ручную модерацию;
- пользователь может создать личную практику для себя;
- публикация личной практики создаёт отдельный модерируемый шаблон для других пользователей;
- LLM не придумывает новые практики, этапы, подзадачи или произвольные ограничения;
- LLM выбирает только из переданного набора и может предложить только заранее описанный вариант
  сложности;
- `enabled=false` полностью исключает практику из автоматической ротации;
- `enabled=true` включает практику в обязательную ротацию с явно заданной частотой;
- отношение пользователя влияет на рекомендуемую частоту, но не подменяет выключатель;
- уровень `unacceptable` переименовывается в `strong_aversion` (`Крайне не хочется`), потому что
  это отношение, а не запрет;
- текущую сессию всегда можно остановить; остановка не выключает практику навсегда и не считается
  согласием на немедленное повторение;
- текущий приоритет — один пользователь и личная эксплуатация; мультипользовательские функции
  не должны усложнять основной сценарий v0.7;
- стек сохраняется: FastAPI, SQLAlchemy async, PostgreSQL, Jinja2, HTMX и TailwindCSS без React.

## 3. Зафиксированный аудит текущего `main`

Исходная точка — commit `7f5d2137022d6d96c3914f03e030243f3d778054`.

### 3.1. Блокирующие дефекты

- чистая установка не воспроизводится: отсутствует `aiosqlite`, а незакреплённая связка
  `passlib`/`bcrypt` несовместима;
- после диагностического восстановления зависимостей остаются 3 падающих теста JSON repair;
- ORM и миграции 005/006 расходятся по FK, JSON/Text, индексам и PostgreSQL boolean defaults;
- приложение вызывает `Base.metadata.create_all()` при старте, обходя Alembic;
- отсутствует роль администратора, а `/admin` доступен обычному пользователю;
- отсутствуют единые object-level проверки владельца;
- повторное завершение одной задачи повторно начисляет награду;
- несколько активных сессий приводят dashboard к ошибке;
- формы изменения состояния не защищены от CSRF;
- пользовательский ввод вставляется через `innerHTML` на нескольких страницах;
- LLM-ответ проверяется синтаксически, но не проверяется на принадлежность разрешённому набору,
  допустимость варианта, параметров, риска и совместимости;
- текущая Training-логика позволяет LLM создавать произвольные подзадачи;
- публичная публикация выполняется без модерации и без версионирования;
- frontend-скрипты ряда страниц отбрасываются из-за отсутствующего блока `scripts` в базовом
  шаблоне;
- runtime CDN, inline JavaScript и смешение `slate`/`gray` делают темы и CSP неконтролируемыми.

### 3.2. Документационные противоречия

- `CONTEXT.md` утверждает, что код ещё не написан;
- `STATUS.md` одновременно объявляет фазы завершёнными и перечисляет непроверенные части;
- ADR-008 и ADR-009 не соответствуют актуальной логике отношения и модерации;
- заявленные результаты тестов не соответствуют чистой установке;
- версии проекта расходятся между `pyproject.toml`, приложением, README и commit message.

## 4. Непереговорные инварианты

Любое изменение принимается только при сохранении всех инвариантов ниже.

### 4.1. Допуск и текущая готовность

| Понятие | Значение | Эффект |
| --- | --- | --- |
| `catalog_status` | Результат модерации шаблона | Только разрешённый шаблон может публиковаться |
| `enabled` | Постоянный пользовательский выключатель | `false` — никогда не участвует в автоматической ротации |
| `attitude_level` | Отношение к включённой практике | Предлагает начальную частоту и влияет на filler-вес |
| `automation_allowed` | Разрешение на автоматическое назначение | `false` — только ручной запуск, даже если практика включена |
| `target_interval` | Желаемый интервал повторения | Определяет `next_due_at` |
| `max_interval` | Максимальный перерыв | Определяет `must_schedule_by` |
| `session_decision` | Решение выполнить пункт сейчас | Можно выбрать `complete`, `stop` или `skip` |

Параметры независимы. Нельзя выводить `enabled` из отношения, риск из рейтинга или текущее
согласие из исторического opt-in.

### 4.2. Ротация

- выключенная практика не появляется ни в кандидате, ни в LLM-контексте, ни в плане;
- включённая и автоматизируемая практика не может исчезнуть из ротации из-за вероятностного
  выбора;
- максимальный интервал обеспечивается детерминированным планировщиком, а не промптом;
- LLM не может удалить обязательный кандидат;
- если все обязательные пункты физически не помещаются, система показывает конфликт и перенос,
  а не молча отбрасывает часть списка;
- ручная практика, срок которой подошёл, показывается отдельным блоком `Требует ручного решения`,
  но не запускается автоматически.

### 4.3. Выполнение и остановка

- действие `Остановить` доступно на каждом активном пункте без дополнительных условий;
- остановка атомарно прекращает текущий пункт и не запускает замену или усложнение автоматически;
- после остановки исходный срок сохраняется, но действует `retry_not_before_at`, чтобы практика
  не возвращалась в ту же сессию;
- цифровая геймификация может не начислить награду за незавершённый пункт; отрицательные баллы
  за остановку выключены по умолчанию и не могут блокировать интерфейс;
- физические последствия, автоматическая эскалация и обязательная компенсационная практика
  не допускаются в автоматическом контуре;
- повторная отправка `complete`, `stop` или `skip` идемпотентна.

### 4.4. LLM

- модель получает конечный список кандидатов и конечный список вариантов;
- модель возвращает только ID, порядок, вариант и разрешённые структурированные параметры;
- свободный текст модели не становится инструкцией практики;
- результат модели не сохраняется до полной серверной валидации;
- отказ модели, невалидный JSON или запрещённый ID не изменяет состояние ротации;
- приложение работоспособно без LLM: детерминированный план доступен отдельной явной кнопкой.

### 4.5. Приватность

- личная практика, история, заметки, замеры, инвентарь и тексты LLM по умолчанию приватны;
- публикация создаёт очищенный снимок шаблона и никогда не переносит историю пользователя;
- исходный ответ LLM не нужен для подсчёта токенов и стоимости;
- постоянное хранение `raw_llm_response` выключено;
- ключ шифрования API-ключей отделён от JWT-секрета;
- публичный Git не содержит реальных пользовательских данных или чувствительного seed-каталога.

## 5. Целевая архитектура приложения

### 5.1. Слои

Роутеры должны быть тонкими. Целевая структура:

```text
app/
  api/                 # HTTP-ввод, auth dependencies, сериализация ответа
  services/            # транзакционные use cases
    catalog.py
    moderation.py
    scheduler.py
    planner.py
    execution.py
    feedback.py
  repositories/        # запросы к БД, всегда с явным user/role scope
  models/              # SQLAlchemy-модели
  schemas/             # Pydantic-контракты и enum
  llm/                 # transport, DTO, prompt builder, validator
  web/                 # page context и HTMX partial handlers
  templates/
  static/
```

Запрещено помещать расчёт ротации, начисление баллов или переходы состояния непосредственно в
роутер или Jinja-шаблон.

### 5.2. Целевая модель данных

Существующий `Entity` совмещает шаблон каталога, личную практику и настройки пользователя.
В v0.7 эти роли разделяются.

| Модель | Назначение | Ключевые поля/ограничения |
| --- | --- | --- |
| `PracticeTemplate` | Версионированное содержание практики | `family_id`, `version`, `status`, `owner_id`, `title`, `description`, `category`, `tags`, `params_schema`, `phase_schema`, `risk_level`, `automation_allowed`; уникально `(family_id, version)` |
| `PracticeVariant` | Заранее утверждённый вариант сложности | `template_id`, `code`, `difficulty 1..5`, `parameter_values`, `instruction_steps`, `duration_min/max`, `automation_allowed`; уникально `(template_id, code)` |
| `UserPractice` | Персональная настройка ротации | `user_id`, `template_id`, `enabled`, `attitude_level`, `target_interval_hours`, `max_interval_hours`, `min_rest_hours`, `max_difficulty`, `next_due_at`, `must_schedule_by`, `last_completed_at`, `retry_not_before_at`; уникально `(user_id, template_id)` |
| `Plan` | План дня или сессии | `user_id`, `local_date`, `timezone`, `status`, `source`, `llm_invocation_id`, `created_at`; не более одного активного плана заданного типа |
| `PlanItem` | Снимок назначенного варианта | `plan_id`, `user_practice_id`, `variant_id`, `position`, `due_reason`, `status`, `snapshot`, `started_at`, `finished_at`, `feedback`; переходы состояния ограничены |
| `ActivityEvent` | Неизменяемый аудит выполнения | `plan_item_id`, `event_type`, `payload`, `idempotency_key`, `created_at`; уникальный `idempotency_key` |
| `ModerationEvent` | История публикации и решений | `template_id`, `actor_id`, `from_status`, `to_status`, `comment`, `created_at` |
| `LLMInvocation` | Метаданные обращения к модели | provider/model, tokens, cost `Numeric`, latency, status, request hash, error code, optional debug payload + `expires_at` |

Дополнительные правила:

- `PracticeTemplate` после публикации неизменяем; изменение создаёт новую версию;
- добавленный пользователем шаблон закреплён на конкретной версии;
- пользователь может уменьшить допуск автоматизации и максимальную сложность, но не повысить их
  выше модераторского ограничения;
- `attitude_level` — enum:
  `want_very_much`, `want`, `neutral`, `reluctant`, `strong_aversion`;
- `risk_level` — enum `not_assessed`, `low`, `elevated`, `high`; `not_assessed` и `high` не
  автоматизируются, `elevated` требует подтверждения перед каждым включением в сессию;
- статусы `PlanItem`: `pending`, `active`, `completed`, `stopped`, `skipped`, `expired`;
- переход из любого финального статуса в другой запрещён;
- награда/транзакция имеет уникальную ссылку на `PlanItem`, поэтому повторное начисление невозможно;
- строки условий геймификации не выполняются через `eval`; используется типизированный набор
  операторов и полей.

### 5.3. Роли

`User.role` принимает `user`, `moderator`, `admin`.

- `user` управляет только собственными данными и создаёт private draft;
- `moderator` читает submitted-снимки и принимает/отклоняет их;
- `admin` дополнительно управляет пользователями, системными шаблонами и настройками;
- доступ к `/admin/*` и `/moderation/*` проверяется сервером, а не наличием ссылки в UI.

## 6. Детерминированный планировщик

### 6.1. Ответственность

`SchedulerService` отвечает за обязательность ротации. LLM отвечает только за компоновку уже
разрешённых элементов.

### 6.2. Расчёт сроков

Начальные значения cadence предлагаются по отношению, но пользователь видит и может изменить
оба числа до сохранения:

| `attitude_level` | `target_interval` | `max_interval` |
| --- | ---: | ---: |
| `want_very_much` | 48 часов | 96 часов |
| `want` | 96 часов | 168 часов |
| `neutral` | 168 часов | 336 часов |
| `reluctant` | 336 часов | 720 часов |
| `strong_aversion` | 720 часов | 1440 часов |

Это только стартовые defaults. После сохранения источником истины являются явные значения
`UserPractice`, а не повторное вычисление по attitude.

При включении практики:

- `next_due_at = enabled_at + target_interval`;
- `must_schedule_by = enabled_at + max_interval`;
- опция `start_immediately` может установить оба срока в `now`.

После `completed`:

- `last_completed_at = finished_at`;
- `next_due_at = finished_at + target_interval`;
- `must_schedule_by = finished_at + max_interval`;
- сложность адаптируется только по отдельной политике.

После `stopped` или `skipped`:

- `next_due_at` и `must_schedule_by` не сдвигаются как при успешном выполнении;
- устанавливается `retry_not_before_at` (по умолчанию `now + 24 hours`);
- пункт не вставляется повторно в текущий план;
- пользователь видит, что практика остаётся просроченной.

### 6.3. Построение плана

Алгоритм выполняется в одной транзакции:

1. выбрать `UserPractice.enabled=true` для пользователя;
2. разделить ручные и автоматизируемые практики;
3. исключить варианты выше `max_difficulty`, нарушающие отдых, риск или совместимость;
4. сформировать `must_include`, где `must_schedule_by <= horizon_end`;
5. сформировать `due`, где `next_due_at <= horizon_end`;
6. сформировать `fillers` из остальных допустимых практик;
7. проверить вместимость обязательного набора по времени и конфликтам;
8. передать LLM только `must_include`, ограниченный набор `due/fillers` и разрешённые варианты;
9. проверить ответ валидатором;
10. создать `Plan` и `PlanItem` со снимками версий;
11. ничего не менять в сроках до фактического результата выполнения.

Порядок обязательных элементов детерминирован: сначала превышение `must_schedule_by`, затем
`next_due_at`, затем стабильный ID. Вероятностный вес применяется только к filler-кандидатам.

### 6.4. Невместимый план

Если обязательный набор не помещается:

- планировщик создаёт максимальный валидный набор по степени просрочки;
- остальные элементы попадают в `carry_over`;
- UI показывает количество и причину переноса;
- событие фиксируется в аудите;
- LLM не разрешается скрывать или переименовывать конфликт.

## 7. LLM-контур

### 7.1. Роль модели

Разрешено:

- выбрать порядок кандидатов;
- выбрать один из разрешённых `variant_id`;
- сгруппировать совместимые пункты в непрерывную сессию;
- предложить краткое нейтральное обоснование на языке пользователя;
- проанализировать агрегированную обратную связь.

Запрещено:

- создавать практику, вариант, фазу, подзадачу или новый параметр;
- менять частоту, максимальный интервал, риск, автоматизацию или пользовательский максимум;
- предлагать ID вне списка;
- усиливать вариант после `stopped`/`too_hard`;
- применять штраф или менять баланс напрямую;
- исполнять tool call, который изменяет данные вне отдельного серверного use case.

### 7.2. Минимальный контракт ответа

```json
{
  "items": [
    {
      "candidate_id": "opaque-id",
      "variant_id": "opaque-variant-id",
      "position": 1,
      "block": "main"
    }
  ],
  "summary_key": "balanced_due_plan"
}
```

`summary_key` разворачивается локальным i18n-словарём. Свободный текст ответа не является частью
задания.

### 7.3. Данные, отправляемые провайдеру

Для удалённых провайдеров по умолчанию действует `abstract`-режим:

- непрозрачный ID;
- категория нагрузки;
- длительность;
- difficulty;
- due/overdue;
- допустимые варианты;
- агрегированная история без личных текстов.

Реальные названия и инструкции раскрываются сервером после валидации. `full`-режим допустим только
для явно выбранного пользователем провайдера и отдельной настройки. Для чувствительных запросов
нельзя использовать непрозрачную маршрутизацию `model=auto` в `full`-режиме.

### 7.4. Валидация и ошибки

Валидатор обязан проверить:

- все обязательные кандидаты включены или явно попали в валидный `carry_over`;
- каждый ID был в запросе и принадлежит пользователю;
- вариант принадлежит выбранной практике и разрешён пользователю;
- параметры соответствуют Pydantic/JSON Schema;
- нет конфликтов, превышения времени, отдыха или risk gate;
- нет дубликатов;
- порядок непрерывен и позиции уникальны.

Допускается не более трёх полных LLM-вызовов. Логическая ошибка возвращается модели в виде списка
кодов валидации. После третьей ошибки состояние БД не меняется; UI показывает ошибку и действия
`Повторить` и `Собрать без LLM`.

`json_repair` не должен превращать произвольный текст в допустимый объект. После repair результат
всё равно проходит строгую схему ответа.

### 7.5. Логи и стоимость

- токены и стоимость берутся из usage-метаданных и хранятся независимо от текста ответа;
- стоимость хранится в `Numeric`, не `Float`;
- debug payload выключен по умолчанию;
- при ручном включении debug payload шифруется отдельным ключом и получает `expires_at`;
- плановая очистка удаляет истёкшие payload, не удаляя usage-метрики и код результата;
- секрет `CREDENTIALS_ENCRYPTION_KEY` не выводится из `JWT_SECRET_KEY`.

## 8. Каталог и модерация

### 8.1. Жизненный цикл

```text
private_draft -> private_active -> submitted -> in_review -> published
                                           \-> rejected
published -> superseded
любое непубличное состояние -> archived
```

Прямой переход `private_* -> published` запрещён.

### 8.2. Публикация личной практики

При `submit` сервер:

1. создаёт неизменяемый снимок содержания;
2. удаляет персональные заметки, историю, статистику и пользовательские значения;
3. фиксирует автора через публичный псевдоним, а не email;
4. устанавливает `submitted`;
5. создаёт `ModerationEvent`.

Изменения исходной личной практики после отправки не изменяют снимок.

### 8.3. Решение модератора

Модератор проверяет содержание, параметры, варианты, risk level и право автоматизации. Решение
должно содержать actor, timestamp и комментарий. Опубликованная версия неизменяема; исправление
публикуется как новая версия, а пользователю предлагается обновление без автозамены.

## 9. Безопасность и целостность

### 9.1. Аутентификация

- убрать небезопасные production defaults секретов; приложение в production завершается с
  понятной ошибкой при placeholder-значении;
- использовать современный password hash с памятью (Argon2id); до появления реальных аккаунтов
  legacy-совместимость не требуется;
- auth cookie: `HttpOnly`, `Secure` в production, `SameSite=Lax` или строже, ограниченный path;
- logout переводится с GET на POST;
- после смены пароля/удаления аккаунта токены становятся недействительны.

### 9.2. Авторизация

- каждый запрос к пользовательскому объекту фильтруется по `user_id` или проверенной роли;
- общая функция policy не должна принимать решение только по UUID из URL;
- тесты обязаны проверять cross-user read/write для каждого семейства endpoints;
- admin и moderation routes покрываются отдельными role-тестами.

### 9.3. Web security

- CSRF-токен обязателен для всех cookie-authenticated state-changing запросов;
- запрет `innerHTML` с пользовательскими значениями; Jinja autoescape не отключать;
- CSP разрешает скрипты и стили только с текущего origin; runtime CDN отсутствуют;
- параметры redirect проверяются как относительные безопасные пути;
- импорт ограничен размером, типом, количеством строк и транзакцией;
- формулы баллов реализуются типизированным DSL, не Python `eval`;
- auth, LLM и import endpoints получают rate limits;
- ошибки пользователю не содержат секреты, prompt или raw provider response.

### 9.4. Идемпотентность и конкурентность

- финализация `PlanItem` выполняется атомарным `UPDATE ... WHERE status IN (...) RETURNING`;
- повторная финализация возвращает текущий результат без новой награды;
- points ledger имеет уникальный `source_plan_item_id`;
- частичный уникальный индекс запрещает две активные сессии одного типа у пользователя;
- генерация плана использует advisory lock или строковую блокировку состояния ротации;
- фоновые задачи и HTTP используют одинаковые application services.

## 10. База данных и миграции

### 10.1. Стратегия v0.7

Рабочее предположение: production-данных ещё нет. Поэтому предпочтительный путь — одна чистая
initial-миграция v0.7 вместо сохранения ошибочной цепочки 001–006.

Перед удалением или squash миграций исполнитель обязан проверить это предположение. Если найдена
БД, которую нужно сохранить, работа останавливается и сначала готовится отдельная forward-only
миграция с резервной копией и проверкой восстановления.

### 10.2. Требования

- убрать `Base.metadata.create_all()` из lifespan;
- единственный путь изменения схемы — Alembic;
- ORM и миграция используют одинаковые типы: JSONB, FK, UUID, enum/check, defaults;
- PostgreSQL boolean defaults задаются `true/false`, не `0/1`;
- все FK, unique constraints и индексы именованы;
- обязательны уникальности opt-in/user practice, achievement grant, active plan и ledger source;
- `TrainingDay.next_day_suggestion`, subtasks и configs — JSONB, а не Text/String;
- время хранится timezone-aware UTC, пользовательская дата рассчитывается по `User.timezone`;
- downgrade чистой миграции и повторный upgrade тестируются в CI;
- отдельный тест сравнивает ключевые ограничения metadata и реальной PostgreSQL-схемы.

## 11. Зависимости, сборка и CI

### 11.1. Один источник зависимостей

- `pyproject.toml` — единственный редактируемый источник Python-зависимостей;
- lock-файл фиксирует транзитивные версии;
- `requirements.txt`, если нужен Docker, генерируется из lock и не редактируется вручную;
- dev установка и CI используют один путь;
- SQLite допускается только для быстрых unit-тестов; интеграционные тесты выполняются на
  PostgreSQL 15;
- версия приложения хранится в одном месте и используется FastAPI, пакетом и UI.

### 11.2. CI jobs

1. `lint`: Ruff format/check и type check.
2. `unit`: unit-тесты без внешних сервисов.
3. `postgres-integration`: чистая БД, Alembic upgrade, интеграционные тесты.
4. `migration-roundtrip`: upgrade -> downgrade -> upgrade.
5. `frontend-build`: сборка локальных CSS/JS assets.
6. `e2e-smoke`: login, Today, Catalog, complete/stop, темы и RU/EN.
7. `security-smoke`: CSRF, stored XSS fixture, cross-user и duplicate completion.

Ни один job не маскируется `continue-on-error`.

## 12. Frontend v0.7

Полный контракт находится в `DESIGN.md`. Здесь зафиксированы продуктовые границы.

### 12.1. Навигация

Основные пользовательские разделы:

1. `Сегодня` — план, текущий пункт, обязательность и один главный CTA;

Admin/moderation не являются пунктами пользовательской навигации.

### 12.2. Обязательные исправления shell

- `base.html` содержит `title`, `head`, `content`, `scripts`;
- активный пункт навигации определяется серверным `active_nav`;

- Tailwind, HTMX, иконки и Chart.js поставляются локально;

- сервер рендерит истинные значения, JavaScript не пересчитывает XP/балансы из графиков;
- пользовательский текст создаётся через HTMX/Jinja или `textContent`, не `innerHTML`.

### 12.3. Вторичные функции

- не показываются на главной;
- доступны только через `Ещё` и feature flags;

- не расширяются новыми функциями в рамках v0.7.
